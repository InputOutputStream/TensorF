Distributed training

Federated learning

TensorF trains a shared model across machines that never exchange raw data — only weight deltas or soft-label logits cross the network. Two modes are implemented: FedAvg (classic weight averaging) and FedDistill (logit-consensus distillation), built on top of a chunked TCP protocol designed to keep peak memory bounded regardless of model size.

FedAvg vs. FedDistill

FedAvgFedDistill
What crosses the wireFull model weight deltas (or the full flat weight vector)Soft-label logit vectors over a shared probe batch
Aggregation mathElementwise mean of client deltas, applied to the global modelElementwise mean of client logits → a consensus target tensor
Where aggregation runsServer::round_accum directly (chunked, streamed)Trainer::aggregate_logits()
Client updateReceives the new global weights, overwrites local modelReceives the consensus logits, trains locally against them (Trainer::distill_logits())
Bandwidth per roundO(model size) — every parameter, every roundO(probe_batch × vocab_size) — usually far smaller than full weights, and independent of model depth
Natural fit forHomogeneous model architecture across all clientsHeterogeneous clients — e.g. a GPTLoRA student per client, since only the logits need to match, not the architecture

The split, as documented directly in Server.hpp's header comment:

  • Server — pure networking: socket/round lifecycle plus chunked FedAvg aggregation (round_accum, a running-sum accumulator updated per client, streamed rather than buffering every client's full weight vector simultaneously).
  • Trainer<Model,T> — FedDistill consensus math (aggregate_logits()) plus checkpointing/serialization. Still exposes aggregate()/get_flat_weights()/set_flat_weights() for round-trip tests, but the live FedAvg path in Server doesn't call them directly.

Trainer<Model, T> — ownership contract

A single class owns the optimizer and every training/aggregation operation, for any Model type exposing forward(inputs, targets, apply_mask), parameters(), and get_vocab_size().

enum TrainMode { FINETUNE, DISTILL, FEDAVG, FEDMETA, FEDDISTILL };

Client side (mode = FEDAVG | FEDDISTILL)

Owns the student model only — no teacher model ever loaded client-side.

finetune()Local training steps for a FedAvg local round
compute_logits()Forward-only pass — FedDistill phase 1 (produce this client's logits for the probe batch)
distill_logits()Trains against the server-supplied consensus tensor. The "teacher" here is a Tensor_t<T> received over the wire, not a live model — the client never loads an actual teacher network.

Server side (mode = FEDAVG | FEDDISTILL, lr = 0)

Owns the global model (also the teacher signal source, when relevant).

aggregate()FedAvg: averages client deltas, overwrites the global model
aggregate_logits()FedDistill: averages client logit vectors into a consensus tensor
get_flat_weights()Serializes the global model for broadcast
set_flat_weights()Deserializes a received flat buffer back into the global model

Server never calls finetune()/distill() — the optimizer object is present but effectively inert (lr = 0 guarantees zero effect if step() is ever called by accident).

Selective training via SFINAE

If Model exposes lora_parameters() (as GPTLoRA<T> does), Trainer's optimizer is built from that instead of the full parameters():

namespace trainer_detail {
    template<typename M, typename = void>
    struct has_lora_parameters : std::false_type {};
    template<typename M>
    struct has_lora_parameters<M, std::void_t<decltype(std::declval<M&>().lora_parameters())>>
        : std::true_type {};
}

This is what makes "client owns a small LoRA adapter on a frozen backbone" actually train as a small adapter rather than a full model — nothing changes for model types that don't define lora_parameters() (plain GPT<T>), which fall through to ordinary parameters()-based behavior untouched.

Wire protocols

Client<T> implements three, layered on io_utils.hpp's read_exact/write_exact:

1. Flat-tensor protocol

send    → [uint64 total_bytes][T × N]
receive ← [uint64 total_bytes][T × N]

Kept for reference and round-trip tests. The actual FedAvg weight exchange does not use this — it uses the chunked protocol below instead.

2. Chunked flat-tensor protocol

Same logical payload as above, but streamed in caller-chosen pieces:

sendChunked    → [uint64 total_elems] then [uint64 chunk_len][T × chunk_len] …
receiveChunked ← same

Peak extra memory is ~chunk_elems × sizeof(T) instead of the entire model's size at once — this is the concrete mechanism that lets a memory-constrained client (see Profiler) participate without ever materializing a full second copy of the model in RAM during transfer.

3. Logits protocol

sendLogits    → probe-batch logits, FedDistill phase 1
receiveLogits ← server's aggregated consensus tensor, FedDistill phase 2

Batch protocol (server → client)

Used when the server streams training data to a client rather than the client sourcing its own local corpus:

receive ← [uint64 batch_size][uint64 block_size]
           [T × batch*block  inputs]
           [T × batch*block  targets]

Server<T>

Owns: the global GPT<T> model, a Trainer<GPT<T>,T>, the TCP listener socket, a ThreadPool, and FedAvg round state (round_accum, client_sockets[], parameter layout).

Thread pool sizing is not a fixed constant handleClient()/handleClientLogits() loop for the entire lifetime of each client connection (see the round-completion condition variable), so every connected client permanently occupies one pool thread for its whole session. The pool is sized to min_clients (plus headroom) in the constructor body, computed once min_clients is known — a flat default would either starve a larger cluster or sit mostly idle for a small one.

ThreadPool has no default constructor and isn't movable/copyable (it owns std::thread/mutex/condition-variable members directly), so it's held as std::unique_ptr<ThreadPool> rather than a plain member — it literally can't be constructed before min_clients is available.

Protocol/ — the profiling wire format

A separate binary MessageProtocol used specifically for a client's initial hardware-profile handshake with the server (the Profiler::to_json() payload described on the Profiler page), with integrity checking selectable per deployment:

CRC32Fast, adequate for trusted LAN clusters
xxHashStronger, used when clients connect over an untrusted WAN

Running a small cluster

terminal 1 — server
make server
./bin/server --port 9000 --min_clients 2 --mode fedavg \
              --model SLM/gpt2-small-f32.gguf
terminal 2+ — each client
make client
./bin/client --server 127.0.0.1 --port 9000 --data Dataset/

Flags shown are illustrative of the parameters Server/Client expose (host/port, minimum clients to start a round, training mode, model/data paths); check include/net/Network/Server.cpp/Client.cpp's main() for the exact CLI surface in your checked-out revision, since Server.hpp/Client.hpp define the reusable class and the .cpp files define the actual executable entry points.

One FedAvg round, end to end

  1. Client connects, sends its hardware profile (Protocol/ handshake).
  2. Server waits until min_clients are connected, then broadcasts current global weights (chunked protocol) to each client.
  3. Each client runs local training steps via Trainer::finetune() for a configured number of local epochs/steps.
  4. Each client computes its weight delta and streams it back (sendChunked).
  5. Server accumulates every client's delta into round_accum as it streams in — no need to hold all clients' full deltas in memory simultaneously.
  6. Once every expected client has reported, the server averages round_accum and applies it to the global model.
  7. Repeat from step 2 for the next round.
