Gateway API — web dashboard backend

gateway/ is a standalone Boost.Beast HTTP + WebSocket server that sits in front of the compiled TensorF binaries (server, client, benchmark, gpt2, smollm, tests) and exposes a REST + realtime API so a web dashboard can start, stop, and watch training/federated jobs without any changes to TensorF's own C++ code. It launches each binary as a child process, captures its stdout/stderr line by line, and fans those lines out over a WebSocket.

Running it

The gateway builds from the root Makefile alongside the rest of TensorF — no separate build step.

make gateway              # builds bin/tensorf-gateway
make run-gateway          # build + run (PORT=8080, TENSORF_BIN_DIR=./bin by default)

# equivalent by hand:
TENSORF_BIN_DIR=./bin ./bin/tensorf-gateway --port 8080

/api/jobs/serverPOSTLaunches bin/server (federated). Body: {"port": N}

Job object shape

{
  "id": "18c6e4c862c2737e-0",
  "kind": "tests",
  "command": "/path/to/bin/basic_tests",
  "pid": 724,
  "status": "running",  // running | exited | failed | killed
  "running": true,
  "exit_code": 0,
  "log_seq": 112,          // total lines produced so far
  "log": [ "=== 1D ===", "[PASS] 1D dot", ... ]
}

WebSocket — /ws

Every connected dashboard receives every event, in real time, as newline-delimited JSON text frames:

TypePayloadWhen
job_started{"type":"job_started","job":{...}}Right after a job is launched via any POST /api/jobs/* route
log{"type":"log","job_id":"...","line":"..."}Each time the job writes a line to stdout/stderr
Not yet implemented A job_exited broadcast (with final status/exit code) is planned but not wired up yet — poll GET /api/jobs/{id} for now to know when a job finished.

Design notes

  • Jobs are launched with fork()/execv(), and the gateway's own event loop is deliberately single-threaded — mixing fork() with a multithreaded io_context is a known Boost.Asio hazard (other threads can leave internal locks held across the fork). Per-job stdout capture still runs on its own reader thread, spawned safely after the fork.
  • The gateway is stateless across restarts: job history lives in memory only, so restarting tensorf-gateway clears the job list. Long-running jobs (a federated server) will keep running as orphaned processes if the gateway restarts — kill them manually via pid/pkill if needed.
  • CORS is wide open (Access-Control-Allow-Origin: *) since this is meant to run on localhost behind your own reverse proxy/auth if exposed beyond that.
