Profiler — hardware-aware hyperparameters

Before a federated client trains a single step, it fingerprints its own hardware and derives a batch size, block size, thread count, and quantization policy tuned to that specific machine. This is what lets one federated round include a Raspberry Pi and a 32-core workstation without either one being the bottleneck by accident.

HardwareFingerprint

Detects everything downstream decisions are based on, using only Linux sysfs/procfs — no external profiling dependency.

CategoryDetected fields

BenchmarkRunner

Runs short real matmul probes at several tile sizes to find the l3_optimal_n matrix dimension — the size at which working set stops fitting in L3 cache and GFLOPS falls off — feeding directly into the batch-size derivation below.

HyperparamAdvisor

The decision engine. Given a fingerprint + benchmark, produces an AlgoPolicy and a HyperparamConfig.

AlgoPolicy
struct AlgoPolicy {
    int  num_threads        = 1;      // OMP_NUM_THREADS recommendation
    QuantPolicy quant         = QuantPolicy::NONE;
    bool dequant_on_the_fly = false;  // dequantize each layer at inference time
};

enum class QuantPolicy { NONE, /* float32, no quantization */
                     FP8_E4M3 /* needs AVX-512 + explicit dequant */, ... };
HyperparamConfig
struct HyperparamConfig {
    size_t batch_size = 128;
    size_t block_size = 1024;
    AlgoPolicy algo;
    // ... n_embed, n_layers used internally during derivation
};

Derivation order

  1. Quantization policy — selected first, from ISA capability and RAM pressure (weaker ISA or tighter RAM → more aggressive quantization).
  2. block_size — constrained by available RAM minus the model's parameter footprint. KV cache size is 2 × n_layers × block_size × n_embed × bytes_per_param; the advisor solves for the largest block_size (rounded down to a power of 2) that fits the remaining RAM budget.
  3. batch_size — constrained by L3 cache: the target is keeping one layer's KV cache plus activations resident in L3. Uses bench.matmul.l3_optimal_n from the benchmark step, divided by block_size, then clamped to [1, 64].
Why this order matters Quantization is chosen before block_size/batch_size because it directly changes bytes_per_param, which both later steps depend on — deriving them in the other order would use a stale byte-width assumption.

Profiler — orchestration & serialization

void run(size_t vocab_size=50257, bool verbose=true)

Runs fingerprinting, benchmarking, and advisory derivation in sequence.

profile_load(fn)Wraps a checkpoint-loading callable, recording peak RSS during that stage
profile_train_step(fn)Same, for a training step
profile_infer_step(fn)Same, for an inference step
print_summary()Human-readable console report of everything detected/decided
to_json()Serializes the full fingerprint + policy + memory profile to a JSON string, exactly what's transmitted to the federated Server as part of client registration

MemoryProfiler

Measures peak resident-set-size deltas around a workload callable (via /proc/self/status), tagged by stage (LOADED, TRAIN, INFER). This is what tells the advisor "the model actually used X MB during a real forward/backward pass," closing the loop against the purely static parameter-count estimate used during initial block_size derivation.

Usage

Profiler p;
p.run(/*vocab_size=*/50257);
p.print_summary();

std::string payload = p.to_json();
// send `payload` to Server as part of the client's REGISTER handshake —
// see federated.html for the wire protocol
