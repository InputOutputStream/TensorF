ModelLoader — GGUF weight loading

Populates a real GPT<T> or Llama<T> from a GGUF checkpoint — the same file format used by llama.cpp. Understanding the shape contract here matters more than the method list: get it wrong and weights load silently transposed.

The weight-shape contract

GGUF layout vs. Matrix<T> layout GGUF stores [out, in] PyTorch weights with the fastest-varying dimension first — i.e. on disk as [in, out]. load_tensor() reverses the dimension order while reading, so the resulting Matrix<T> comes out as {out, in} — exactly matching Linear<T>'s own weight convention. Net effect: no .transpose() call is needed anywhere when copying a GGUF tensor into a Linear.weight. This single reversal is why the loader code below never transposes attention or MLP projection weights.
GGUF tensor namePyTorch shapeMatrix<T> shape after load_tensor()
token_embd.weight[vocab, D]{vocab, D} ✓ matches Embedding table directly
*.attn_qkv.weight (GPT-2 fused)[3D, D]{3D, D} — sliced into 3 × {head_size, D} per head via slice_row, no transpose
*.attn_output.weight[D, D]{D, D} = {out, in} ✓
*.ffn_up.weight[4D, D]{4D, D} = {out, in} ✓
*.ffn_down.weight[D, 4D]{D, 4D} = {out, in} ✓

GPTGGUFLoader<T>

GPT2HyperParams
struct GPT2HyperParams {
    size_t vocab_size = 50257;
    size_t d_model    = 768;
    size_t block_size = 1024;
    size_t n_layer    = 12;
    size_t n_head     = 12;
};
GPT<T> load_model(std::string path, GPT2HyperParams hp)

Opens the GGUF file, constructs an empty GPT<T> skeleton at the given hyperparameters, then walks every block loading Q/K/V (sliced from the fused QKV weight), attention output projection, both LayerNorms, and the GeLU MLP's up/down projections. Prints a per-layer progress log and a final parameter-count report.

GPT2Tokenizer load_tokenizer()

Reads the tokenizer.ggml.tokens and tokenizer.ggml.merges metadata arrays embedded in the same GGUF file and builds a ready-to-use GPT2Tokenizer. Warns and returns an empty tokenizer if that metadata is absent from the checkpoint.

LlamaGGUFLoader<T>

LlamaHyperParams
struct LlamaHyperParams {
    size_t vocab_size;
    size_t input_dim;   // embedding_length,       e.g. 576  (SmolLM2-135M)
    size_t block_size;  // context_length,         e.g. 8192
    size_t n_heads;     // attention.head_count,   e.g. 9
    size_t n_kv_heads;  // attention.head_count_kv,e.g. 3
    size_t n_layer;     // block_count,            e.g. 30
    size_t ffn_hidden;  // feed_forward_length,    e.g. 1536
};
Llama<T> load_model(std::string path, LlamaHyperParams hp)

Same overall shape as the GPT loader — token embedding, per-block RoPE-attention Q/K/V/O projections, RMSNorm weights, and SwiGLU gate/up/down projections.

LlamaTokenizer load_tokenizer()

Same metadata keys as the GPT-2 loader, but additionally splits each merge-rule string on its first space into a (left, right) pair before handing them to LlamaTokenizer::load_from_gguf.

n_kv_heads is parsed but not yet wired up LlamaHyperParams::n_kv_heads is read from GGUF metadata but Llama<T>'s current attention implementation does not do grouped-query attention with a separate KV head count — every head gets its own full Q/K/V, matching n_heads. For SmolLM2-135M where n_heads=9, n_kv_heads=3, this means the loader currently expects (and the model computes with) more K/V weight than a true GQA implementation would use. Worth checking against your specific checkpoint's actual K/V weight shapes before assuming full compatibility.
